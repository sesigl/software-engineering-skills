# Agent-First Repository Setup

You are setting up a Git repository so humans and coding agents can build, verify, and evolve software with fast feedback and deterministic guardrails. Explore the target directory first, interview the user to shape the setup to their stack and domain, confirm the blueprint, and scaffold a repository with executable specifications, path-scoped agent context, and deterministic guardrails.

## Core Design Principles

Every repository generated by this skill is organized around three pillars:

1. **First Make It Work (Problem Solving & Architecture)**:
   - **Attack the Premise & Subtract Before You Add**: Question unnecessary requirements. Delete dead code, obsolete shims, and unused indirection before adding new code. Do not scaffold ports, fakes, or packages that no current `@SPEC-NNN` scenario uses.
   - **Redesign From First Principles & Fix Root Causes**: Fix flaws in the domain model or boundary invariants rather than patching call sites.
   - **Build the Lever**: Codify repeated checks and workflows into deterministic scripts in `scripts/` wired into `Makefile` targets rather than relying on prose reminders in `CLAUDE.md`.
   - **Architecture Discipline**: Match the architecture to the system shape (for example, vertical job slices with a shared pure core for batch pipelines, or ports and adapters for stateful services). Model the domain with exact terms from `GLOSSARY.md`, enforce invariants through types at the boundary, keep core logic pure (I/O at the edges), and enforce module dependency rules deterministically in `make check`.
2. **Then Make It Right (Verification & Quality Signals)**:
   - **Executable Specifications & System-Test-First**: Specify every behavior in `features/` (or `<module>/features/` in a monorepo) as a Gherkin scenario with a unique `@SPEC-NNN` tag. Verify behaviors through the public system boundary using plain input data (for pipelines, libraries, and CLIs) or fast in-memory stores and local fakes (for stateful services). Reserve unit tests for isolated, high-complexity algorithms.
   - **Crapper, Dryer, and Mutator Gates**: Enforce CRAP score (`CRAP < 10`), clone density (`duplication < 0.8%`), and mutation testing (cover the uncovered, kill surviving mutants with behavioral assertions, or delete dead code).
3. **Practice (Context & Execution Hygiene)**:
   - **Guard the Context Window**: Keep `CLAUDE.md` under 120 lines. Scope `.claude/rules/*.md` with YAML `paths:` frontmatter so rules load strictly on demand when matching files are touched. Put procedural guides in `.claude/skills/` and delegate noisy exploration to fresh subagents.
   - **Evergreen Memory & Small Ordered Commits**: Record non-obvious, hard-to-reverse decisions in `docs/adr/`. When a later decision changes an earlier one, add `Amended by NNNN` to the earlier ADR instead of rewriting history. Keep evergreen files (`features/`, `docs/`, `GLOSSARY.md`) free of references to transient scratch or plan files. Sequence changes into small verifiable commits.

## Step 1: Understand the goal and interview on open decisions

Inspect the target directory (`git status`, existing files, language manifests) first. If the user has not yet described what they want to build, ask for the project goal and any existing design docs, schemas, or repositories to read. When the user provides reference docs or names external systems, read them first (using parallel read-only subagents when helpful) so you can answer as many questions as possible yourself.

Do not run a long questionnaire. Infer defaults from the prompt, directory, and reference docs, combine related items into single questions, and ask only what remains open—2 to 4 concise questions at a time, each with a recommended default:

1. **Domain, glossary, and first increment (`@SPEC-001`)**: What the project builds, the first 3 to 5 core domain terms (with real ID types and formats from existing schemas when available), and the first real slice of behavior to specify as `@SPEC-001`.
2. **System shape, topology, and architecture contracts**:
   - **System shape**: request-driven service, batch or data pipeline, library, CLI, or a mix. Select the architecture from the shape instead of defaulting to hexagonal ports and fakes. For a batch pipeline or library, recommend vertical slices plus a shared pure core (`input data -> output data`) tested with plain data.
   - **Topology**: single-context repository (default) or multi-module monorepo.
   - **Architecture enforcement**: deterministic import-boundary contracts in `make check` (`import-linter` for Python, `ArchUnit` for JVM, `dependency-cruiser` for TypeScript/JS) that keep the core pure, keep slices independent, and forbid production code from importing tests.
3. **Tech stack, fast system-test harness, quality bar, and CI**:
   - **Language and strict quality bar**: build tool, strict type checker and linter defaults (for example `mypy --strict`, `ruff` `ALL`, and `pip-audit` for Python), and whether to scaffold a CI workflow (GitHub Actions or Jenkins, optional).
   - **Fast system-test harness**: concrete millisecond-speed setup for their shape and stack (for example plain in-memory data for pure transforms, or SQLite/PGlite/H2 and local fakes for stateful services).
   - **Quality signals**: `make test` runs Gherkin validation, traceability, **Dryer** (`duplication < 0.8%`), **Crapper** (`CRAP < 10` / complexity `< 15`), and fast tests; `make test-all` adds **Mutator** (`>= 80%`).
4. **Target agent harnesses, documentation contract, and external system safety**:
   - **Target agent harnesses**: recommend Claude Code only as the default, and name alternatives such as Codex, Cursor, GitHub Copilot, and Gemini CLI.
   - **Documentation traceability**: which evergreen docs belong in `docs/` alongside `docs/adr/`, and whether `scripts/check-traceability` should require every `@SPEC-NNN` to be annotated in `docs/` (default: off, `REQUIRE_DOC_TRACEABILITY=0`).
   - **External systems (only when applicable)**: any live systems (search index, data warehouse, APIs) that agents may inspect read-only and must never mutate.

Wait for the user's answers and resolve any follow-up questions before proceeding.

If the user selects a harness other than Claude Code, read [`references/agent-harnesses.md`](references/agent-harnesses.md) and research the current conventions of each selected harness before Step 2. Do not rely on remembered file locations or frontmatter keys.

Completion criterion: target agent harnesses, system shape and architecture contracts, domain glossary terms, first behavior slice (`@SPEC-001`), repository topology, tech stack, system-test harness, quality thresholds, and documentation traceability rules are confirmed by the user.

## Step 2: Present the repository blueprint

Present a concise blueprint for approval before writing files:

- **Directory tree**: show the exact folders and files to create, including module or slice layout. Do not include empty `fakes/` or `ports/` directories unless `@SPEC-001` uses them.
- **Architecture contracts**: list the module dependency and purity rules enforced by `make check`.
- **`Makefile` interface**: list the top-level targets (`help`, `check`, `test`, `test-all`, `build`) and the supported parameters (`MODULE=`, `SPEC=`, `FILTER=`, `SCOPE=`), noting that filtered test runs skip coverage-dependent quality gates.
- **Deterministic guardrails (`scripts/`)**: list each script (`check-features`, `check-traceability`, `check-quality`, plus any read-only query helper) and what makes it fail.
- **Agent context**: for Claude Code only, list the path-scoped `.claude/rules/*.md` files with their `paths:` globs and the on-demand `.claude/skills/*/SKILL.md` skills. For other or additional harnesses, show the researched findings with source URLs, the canonical instruction file, each rendered rule file with its scope, and the shared skills directory.

Ask the user to confirm or adjust the blueprint. End your turn and wait for confirmation.

Completion criterion: the user has approved the repository blueprint.

## Step 3: Scaffold repository layout and evergreen foundations

Read [`references/repo-templates.md`](references/repo-templates.md) and create the foundational files tailored to the confirmed blueprint:

1. Initialize Git (`git init`) if `.git/` does not exist, and create `.gitignore` for the selected stack.
2. Write the project instruction file with the project purpose, parameterized `Makefile` commands, directory concepts, architecture contract summary, read-only production safety rules (if external systems exist), and the three-pillar engineering principles (*First Make It Work*, *Then Make It Right*, and *Practice*). For Claude Code only, this file is `CLAUDE.md`. For other or additional harnesses, write the canonical file and the adapters that `references/agent-harnesses.md` describes (for example `AGENTS.md` plus a `CLAUDE.md` that imports it with `@AGENTS.md`).
3. Write `GLOSSARY.md` at the root for a single-context repo, or `GLOSSARY-MAP.md` at the root plus `<module>/GLOSSARY.md` in each module for a monorepo, populated with the user's domain terms and `_Avoid_` synonyms.
4. Create `features/` (or `<module>/features/` per module in a monorepo) with a seed `<capability>.feature` file containing `@SPEC-001` for the user's first real increment, using real domain terms and ID formats.
5. Create `docs/README.md` (defining documentation structure and `@SPEC-NNN` annotation rules), `docs/adr/0001-agent-first-architecture.md` (recording the system shape, architecture contracts, system-test strategy, and quality thresholds), and any reference docs grounded in read-only discovery (marking facts as verified or inferred).
6. Write the root `Makefile` with minimal, parameterized targets (`help`, `check`, `test`, `test-all`, `build`).

Completion criterion: Git is initialized, and the instruction file of each selected harness, `GLOSSARY.md` (or `GLOSSARY-MAP.md`), `Makefile`, `features/`, `docs/README.md`, and `docs/adr/0001-agent-first-architecture.md` exist on disk.

## Step 4: Configure on-demand rules and skills

Read [`references/claude-context-templates.md`](references/claude-context-templates.md) for the rule and skill bodies. The paths below are for Claude Code. For other or additional harnesses, render the same bodies at the researched locations and apply the decision rules in [`references/agent-harnesses.md`](references/agent-harnesses.md): one body per rule topic, one shared skills directory, and no files for harnesses that the user did not select.

1. Create path-scoped rule files in `.claude/rules/` where every file starts at line 1 with `---` and a YAML `paths:` frontmatter block (never wrap the file in a ```` ```markdown ```` code fence):
   - `.claude/rules/features.md` scoped to `features/**/*.feature` and `**/features/**/*.feature`
   - `.claude/rules/testing.md` scoped to test directories and test files
   - `.claude/rules/docs-and-adrs.md` scoped to `docs/**/*.md`, `**/docs/**/*.md`, and `GLOSSARY*.md`
   - `.claude/rules/scripts-and-build.md` scoped to `Makefile`, `scripts/**`, and `**/scripts/**`
   - `.claude/rules/architecture.md` (when applicable) scoped to `src/**` with the purity, boundary, and ID rules for production code
2. Create project-specific skills in `.claude/skills/`:
   - `.claude/skills/system-testing/SKILL.md`: documents the project's system-test harness, how to keep tests fast, when to write unit tests for isolated complex logic, how to tag tests with `@SPEC-NNN`, and how to clear **Crapper** (`CRAP < 10`), **Dryer** (`duplication < 0.8%`), and **Mutator** gates.
   - `.claude/skills/domain-modeling/SKILL.md`: guides challenging ambiguous terms against `GLOSSARY.md`, moving renamed terms to `_Avoid_`, and writing or amending ADRs in `docs/adr/`.
   - `.claude/skills/feature-development/SKILL.md`: guides the end-to-end spec-first workflow (*First Make It Work -> Then Make It Right -> Practice*) from `GLOSSARY.md` and `features/*.feature` (`@SPEC-NNN`) to system test, implementation, refactoring, and small ordered commits.
   - Read-only inspection skills (only when external systems were specified in Step 1): one skill per external system documenting read-only commands or guarded query scripts.

Completion criterion: every rule file starts with valid scope frontmatter (for Claude Code, `---\npaths:`), and the skills directory of each selected harness contains `system-testing`, `domain-modeling`, `feature-development`, and any confirmed external-system inspection skills.

## Step 5: Install deterministic guardrails and verify the loop

Read [`references/guardrails-and-quality.md`](references/guardrails-and-quality.md) and implement the executable guardrails and seed verification loop:

1. Create executable scripts in `scripts/` (`chmod +x`):
   - `scripts/check-features`: validates Gherkin syntax across all `.feature` files (using the official Gherkin parser when installed, plus line checks), enforces that every module in a monorepo has a `features/` folder, and verifies unique `@SPEC-NNN` tags on every scenario.
   - `scripts/check-traceability`: verifies that every `@SPEC-NNN` tag in `features/` is referenced by at least one system test (and annotated in `docs/` when `REQUIRE_DOC_TRACEABILITY=1`), checks that evergreen files (`features/`, `docs/`, `GLOSSARY*.md`) contain no links to transient scratch or plan files, and checks that every `.claude/rules/*.md` file starts with `---`.
   - `scripts/check-agent-context` (only when two or more harnesses are selected): fails when the rendered rules, the instruction adapters, or the mirrored skills drift apart. `make check` runs it.
   - `scripts/check-quality`: runs fast quality signals on `--fast` (**Dryer** duplication `< 0.8%`, **Crapper** `CRAP < 10` / complexity `< 15`) and full quality signals on `--all` (**Mutator** mutation score threshold).
2. Scaffold the minimal project build config, architecture-contract config, the seed system test covering `@SPEC-001`, and the minimal production code to pass it. Do not scaffold unused ports, fakes, or packages.
3. Probe the architecture contract once: add a forbidden import, confirm that `make check` fails, and remove the forbidden import.
4. Run `make test` (and `make test-all` when mutation testing is configured) in the terminal and fix any issues until it exits `0`.

Completion criterion: the architecture contract probe fails as expected when violated, and `make test` runs linting, type checks, architecture contracts, Gherkin validation, `@SPEC-NNN` traceability, fast quality checks, and the `@SPEC-001` system test, and exits `0`.
