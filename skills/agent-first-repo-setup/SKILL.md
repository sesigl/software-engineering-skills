# Agent-First Repository Setup

You are setting up a Git repository so humans and coding agents can build, verify, and evolve software with fast feedback and deterministic guardrails. Explore the target directory first, interview the user to shape the setup to their stack and domain, confirm the blueprint, and scaffold a repository with executable specifications, path-scoped agent context, and deterministic guardrails.

## Core Design Principles

Every repository generated by this skill is organized around three pillars:

1. **First Make It Work (Problem Solving & Architecture)**:
   - **Attack the Premise & Subtract Before You Add**: Question unnecessary requirements and remove dead code, obsolete shims, or unused indirection before adding new code.
   - **Redesign From First Principles & Fix Root Causes**: Fix flaws in the domain model or boundary invariants rather than patching call sites.
   - **Build the Lever**: Codify repeated checks and workflows into deterministic scripts in `scripts/` wired into `Makefile` targets rather than relying on prose reminders in `CLAUDE.md`.
   - **Architecture Discipline**: Model the domain using canonical terms from `GLOSSARY.md`, enforce invariants through the type system at the boundary, keep domain logic pure (I/O at the edges), make state mutations idempotent, and partition state before serializing access to shared state.
2. **Then Make It Right (Verification & Quality Signals)**:
   - **Executable Specifications & System-Test-First**: Specify every behavior in `features/` (or `<module>/features/` in a monorepo) as a Gherkin scenario with a unique `@SPEC-NNN` tag. Verify behaviors through the public system boundary against fast in-memory stores and local fakes; reserve unit tests for isolated, high-complexity algorithms.
   - **Crapper, Dryer, and Mutator Gates**: Enforce CRAP score (`CRAP < 10`), clone density (`duplication < 0.8%`), and mutation testing (cover the uncovered, kill surviving mutants with behavioral assertions, or delete dead code).
3. **Practice (Context & Execution Hygiene)**:
   - **Guard the Context Window**: Keep `CLAUDE.md` under 120 lines. Scope `.claude/rules/*.md` with YAML `paths:` frontmatter so rules load strictly on demand when matching files are touched. Put procedural guides in `.claude/skills/` and delegate noisy exploration to fresh subagents.
   - **Evergreen Memory & Small Ordered Commits**: Record non-obvious, hard-to-reverse decisions in `docs/adr/`. Keep evergreen files (`features/`, `docs/`, `GLOSSARY.md`) free of references to transient scratch or plan files. Sequence changes into small verifiable commits.

## Step 1: Interview the user

Inspect the target directory (`git status`, existing files, language manifests) so you do not ask what the directory already answers. Then interview the user across the open items below. Ask 2 to 4 concise questions at a time and lead each question with a recommended default based on their project type:

1. **Domain and purpose**: What product, service, or library does this repository build, and what are the first 3 to 5 core domain terms for `GLOSSARY.md`?
2. **Repository topology**: Single-context repository (default) or multi-module monorepo? If a monorepo, what are the initial modules?
3. **Tech stack and runtime**: Language, build tool, test framework, and external dependencies (databases, message brokers, external HTTP APIs).
4. **Fast system-test harness**: How should system tests run in milliseconds without external network calls? Propose concrete options for their stack (for example, SQLite/PGlite/H2 or an embedded single-node store, in-memory fakes for external APIs and queues, and shared test server boot) capable of scaling to thousands of system tests.
5. **Quality signals and thresholds**: Propose tools and defaults for the two verification tiers:
   - `make test` (fast loop): Gherkin syntax check, `@SPEC-NNN` traceability check, **Dryer** (`duplication < 0.8%`), **Crapper** (`CRAP < 10` / Cognitive Complexity `< 15`), and the fast system test suite.
   - `make test-all` (full loop): everything in `make test` plus **Mutator** (mutation testing >= 80%, killing survivors or deleting dead code).
6. **Documentation contract**: Which documents belong in `docs/` alongside `docs/adr/`, and should `scripts/check-traceability` require every `@SPEC-NNN` scenario to be annotated in `docs/` as well as in `tests/`?

Wait for the user's answers and resolve any follow-up questions before proceeding.

Completion criterion: domain purpose, initial glossary terms, repository topology, tech stack, system-test harness design, quality signal tools and thresholds, and documentation traceability rules are confirmed by the user.

## Step 2: Present the repository blueprint

Present a concise blueprint for approval before writing files:

- **Directory tree**: show the exact folders and files to create, including module layout if a monorepo was selected.
- **`Makefile` interface**: list the top-level targets (`help`, `check`, `test`, `test-all`, `build`) and the supported parameters (`MODULE=`, `SPEC=`, `FILTER=`, `SCOPE=`).
- **Deterministic guardrails (`scripts/`)**: list each script (`check-features`, `check-traceability`, `check-quality`) and what makes it fail.
- **Claude Code context (`.claude/`)**: list the path-scoped `.claude/rules/*.md` files with their `paths:` globs and the on-demand `.claude/skills/*/SKILL.md` skills.

Ask the user to confirm or adjust the blueprint. End your turn and wait for confirmation.

Completion criterion: the user has approved the repository blueprint.

## Step 3: Scaffold repository layout and evergreen foundations

Read [`references/repo-templates.md`](references/repo-templates.md) and create the foundational files tailored to the confirmed blueprint:

1. Initialize Git (`git init`) if `.git/` does not exist, and create `.gitignore` for the selected stack.
2. Write `CLAUDE.md` with the project purpose, parameterized `Makefile` commands, directory concepts, and the three-pillar engineering principles (*First Make It Work*, *Then Make It Right*, and *Practice*).
3. Write `GLOSSARY.md` at the root for a single-context repo, or `GLOSSARY-MAP.md` at the root plus `<module>/GLOSSARY.md` in each module for a monorepo, populated with the user's initial domain terms and `_Avoid_` synonyms.
4. Create `features/` (or `<module>/features/` per module in a monorepo) with a seed `<capability>.feature` file containing `@SPEC-001`.
5. Create `docs/README.md` (defining documentation structure and `@SPEC-NNN` annotation rules) and `docs/adr/0001-agent-first-architecture.md` (recording the repository topology, system-test-first strategy, and quality thresholds).
6. Write the root `Makefile` with minimal, parameterized targets (`help`, `check`, `test`, `test-all`, `build`).

Completion criterion: Git is initialized, and `CLAUDE.md`, `GLOSSARY.md` (or `GLOSSARY-MAP.md`), `Makefile`, `features/`, `docs/README.md`, and `docs/adr/0001-agent-first-architecture.md` exist on disk.

## Step 4: Configure on-demand `.claude/rules/` and `.claude/skills/`

Read [`references/claude-context-templates.md`](references/claude-context-templates.md) and create the Claude Code configuration:

1. Create path-scoped rule files in `.claude/rules/` where every file starts with YAML `paths:` frontmatter so rules load strictly on demand when Claude accesses matching files:
   - `.claude/rules/features.md` scoped to `features/**/*.feature` and `**/features/**/*.feature`
   - `.claude/rules/testing.md` scoped to test directories and test files
   - `.claude/rules/docs-and-adrs.md` scoped to `docs/**/*.md`, `**/docs/**/*.md`, and `GLOSSARY*.md`
   - `.claude/rules/scripts-and-build.md` scoped to `Makefile`, `scripts/**`, and `**/scripts/**`
2. Create project-specific skills in `.claude/skills/`:
   - `.claude/skills/system-testing/SKILL.md`: documents the project's system-test harness, in-memory database and fake setup, how to keep thousands of system tests fast, when to write unit tests for isolated complex logic, how to tag tests with `@SPEC-NNN`, and how to clear **Crapper** (`CRAP < 10`), **Dryer** (`duplication < 0.8%`), and **Mutator** gates.
   - `.claude/skills/domain-modeling/SKILL.md`: guides challenging ambiguous terms against `GLOSSARY.md`, updating domain terms inline, and writing ADRs in `docs/adr/` when decisions are hard to reverse, surprising without context, and based on a real trade-off.
   - `.claude/skills/feature-development/SKILL.md`: guides the end-to-end spec-first workflow (*First Make It Work -> Then Make It Right -> Practice*) from `GLOSSARY.md` and `features/*.feature` (`@SPEC-NNN`) to system test, implementation, refactoring, and small ordered commits.

Completion criterion: every file in `.claude/rules/` has valid YAML `paths:` frontmatter, and `.claude/skills/` contains `system-testing`, `domain-modeling`, and `feature-development` tailored to the project stack.

## Step 5: Install deterministic guardrails and verify the loop

Read [`references/guardrails-and-quality.md`](references/guardrails-and-quality.md) and implement the executable guardrails and seed verification loop:

1. Create executable scripts in `scripts/` (`chmod +x`):
   - `scripts/check-features`: validates Gherkin syntax across all `.feature` files, enforces that every module in a monorepo has a `features/` folder, and verifies unique `@SPEC-NNN` tags on every scenario.
   - `scripts/check-traceability`: verifies that every `@SPEC-NNN` tag in `features/` is referenced by at least one system test (and annotated in `docs/` when documentation coverage is enabled), and checks that evergreen files (`features/`, `docs/`, `GLOSSARY*.md`) contain no links to transient scratch or plan files.
   - `scripts/check-quality`: runs fast quality signals on `--fast` (**Dryer** duplication `< 0.8%`, **Crapper** `CRAP < 10` / complexity `< 15`) and full quality signals on `--all` (**Mutator** mutation score threshold).
2. Scaffold the minimal project build config, the fast system-test harness (with any configured in-memory store or fake), and the seed system test covering `@SPEC-001`.
3. Run `make test` (and `make check`) in the terminal and fix any issues until it exits `0`.

Completion criterion: `make test` runs Gherkin validation, `@SPEC-NNN` traceability, fast quality checks, and the `@SPEC-001` seed system test, and exits `0`.
